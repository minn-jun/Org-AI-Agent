# 파라미터와 설계 근거

갱신일: 2026-09-28
대상: `org_agent_mvp` 전체

이 문서는 코드에 들어간 **모든 수치가 어디서 왔는지**를 기록한다.
값이 임의인 것은 임의라고 적는다. 측정으로 정한 것은 측정값을 함께 적는다.

수치를 바꿔야 할 때 이 문서를 먼저 보고, 바꾼 뒤에는 이 문서를 갱신한다.

---

## 0. 값의 신뢰 등급

표에 붙는 등급의 뜻은 다음과 같다.

| 등급 | 의미 |
|---|---|
| **측정** | 평가셋으로 여러 값을 비교해 고른 값 |
| **유도** | 다른 제약에서 논리적으로 따라 나온 값 |
| **관례** | 일반적인 관행을 따른 값. 근거는 약하다 |
| **임의** | 처음 구현할 때 정한 값. 검증되지 않았다 |

**현재 대부분의 값은 임의 또는 관례다.** 이것이 이 프로토타입의 가장 큰 한계다.

## 2. Prefetch 파라미터

### 2-1. `TIER_PRIOR_ALPHA = 1.0`

| 항목 | 내용 |
|---|---|
| 하는 일 | `최종점수 = 정규화점수 × (1 + α × tier가중치)` |
| 등급 | **측정** (다만 아래 2026-10-07 결과를 함께 볼 것) |
| 근거 | α=0 대비 F1 27.3% → 27.6%. 차이는 작지만 방향은 일관됨 |
| 범위 | 0이면 계층 무시(ablation), 값이 커질수록 계층이 지배 |

**2026-10-07 실제 자료 어블레이션 — 1위를 바꾸지 못한다.** 진행 중 과제를 세 계층에
올리고 라우팅 80문항으로 재 보니, α를 0으로 둬도 `tier@1`이 **같았다**(64/68).
`tier@3`만 1건 차이였다.

| 설정 | 단일 계층 tier@1 | tier@3 | 계층 혼합 coverage |
|---|---|---|---|
| 기본 (α=1, floor=1) | 64/68 | **67/68** | **12/12** |
| α=0 | 64/68 | 66/68 | 12/12 |
| floor=0 | 64/68 | 67/68 | **10/12** |

위 F1 27.3 → 27.6은 **합성 STM/MTM** 환경의 값이다. 실제 자료에서는 어휘가 계층별로
충분히 갈려서 prior가 할 일이 없는 것으로 보인다. **빼자는 뜻은 아니다** — 자료가
섞이는 환경에서는 다를 수 있다. 다만 **이 값이 성능을 만든다고 말할 근거는 없다.**

**왜 곱셈인가.** 이전 구현은 `점수 + 가중치 × 5.0`이었다. 가산이면 관련성이 0인
문서도 계층 보너스만으로 점수를 얻는다. 곱셈이면 `0 × 1.7 = 0`이라 걸러진다.

**왜 5.0이 문제였나.** 검색 점수 범위가 질문마다 다르다(0~3 또는 0~50).
보너스가 고정 상수면 점수가 낮은 질문에서는 계층이 관련성을 덮어쓰고,
높은 질문에서는 아무 영향이 없다. **같은 상수가 질문마다 다르게 동작했다.**

### 2-2. `PREFETCH_POOL_PER_TIER = 20`

| 항목 | 내용 |
|---|---|
| 하는 일 | 계층별로 몇 건까지 후보로 수집할지 |
| 등급 | **임의** |
| 근거 | 최종 8건의 2~3배면 순위 경쟁이 성립한다고 보고 정함 |
| 위험 | 문서가 수천 건이 되면 20건은 부족할 수 있다. 재검토 필요 |

### 2-3. `PREFETCH_CUT_RATIO = 0.3`

| 항목 | 내용 |
|---|---|
| 하는 일 | `컷 = 0.3 × 최고점`. 이 아래는 버린다 |
| 등급 | **임의** |
| 근거 | 절대 임계값은 코퍼스가 바뀌면 스케일이 흔들려서 상대값으로 정했다 |
| 성질 | 최고점 문서는 항상 통과하므로 후보가 있으면 최소 1건은 나온다 |

**상대값을 쓴 이유가 핵심이다.** 절대값(예: "점수 5 이상")은 코퍼스나
쿼리 확장이 바뀌면 의미가 달라진다. 상대값은 그 영향을 받지 않는다.

다만 0.3이라는 숫자 자체는 근거가 없다. 튜닝 대상이다.

### 2-4. `PREFETCH_MIN_CARDS = 1`

| 항목 | 내용 |
|---|---|
| 하는 일 | 후보가 있으면 최소 이만큼은 반환 |
| 등급 | **유도** |
| 근거 | 컷이 이미 최소 1건을 보장하므로 1은 사실상 무동작 방어선 |
| 주의 | 2 이상으로 올리면 **컷 아래 문서를 강제로 넣게 된다** |

처음에는 2였다. 측정해 보니 컷 임계값 1.615인데 1.194짜리 문서가
강제로 들어가고 있었다. 컷 로직을 무력화하므로 1로 낮췄다.

### 2-5. `PREFETCH_TIER_FLOOR = 1`

| 항목 | 내용 |
|---|---|
| 하는 일 | 가중치가 0이 아닌 계층마다 최소 이만큼 자리 보장 |
| 등급 | **측정** (다만 차이가 작다) |
| 근거 | 아래 측정표 참조 |

**이 파라미터는 측정 결과 때문에 추가됐다.** 문서를 115건으로 늘리자
순수 전역 순위가 구 쿼터 방식보다 재현율이 낮게 나왔다. 원인은
한 계층이 상위를 독점해 다른 계층의 정답이 밀려나는 것이었다.

즉 **쿼터에는 낭비만 있는 게 아니라 다양성 보장이라는 기능도 있었다.**
처음 진단에서 이 측면을 놓쳤다.

옛 쿼터와 다른 점은 **이미 컷을 통과한 문서 중에서만 자리를 보장**한다는 것이다.
관련 없는 문서를 끌어오지 않는다.

**2026-10-07 — 이 파라미터는 계층 혼합 질문에서 일한다.** 라우팅 80문항 중 기대
계층이 둘인 12문항에서, floor=0으로 두면 두 계층을 모두 가져온 문항이
**12/12 → 10/12**로 줄었다. 단일 계층 질문에서는 차이가 없다(64/68 동일).
`TIER_PRIOR_ALPHA`와 역할이 다르다 — **깊이는 대목 수가, 폭은 이 값이 정한다.**

### 2-6. `PREFETCH_TOP_K = 8`

| 항목 | 내용 |
|---|---|
| 하는 일 | 컨텍스트에 넣을 근거 상한 |
| 등급 | **관례** |
| 근거 | 초기 구현값을 유지. 컨텍스트 예산과 정밀도의 절충 |
| 참고 | A방식 이후 실제 반환 건수는 가변이다 (평균 7.0건) |

## 3. 측정 결과 — 무엇을 목표로 했고 무엇이 나왔나

### 3-1. 처음 세운 가설

> 계층 가중치를 자리 수(쿼터)가 아니라 점수 prior로 바꾸면
> 무관한 문서가 줄고 정밀도가 오른다.

### 3-2. 문서 28건 측정 (2026-09-01 오전)

| 모드 | 정밀도@8 | 재현율 | F1 | 평균 근거 |
|---|---|---|---|---|
| quota | 20.0% | 100% | 33.4% | 7.20 |
| prior α=0 | 22.1% | 100% | 36.2% | 6.67 |
| prior α=1 | **23.2%** | 100% | **37.6%** | 6.40 |

가설이 지지되는 것처럼 보였다.

### 3-3. 문서 115건 측정 (2026-09-01 오후)

| 설정 | 정밀도@8 | 재현율 | F1 |
|---|---|---|---|
| quota (구방식) | 17.0% | 74.2% | 27.7% |
| prior α=0 | 16.8% | 72.6% | 27.3% |
| prior α=1, floor=1 | 17.1% | 71.0% | 27.6% |
| prior α=1, floor=2 | **17.5%** | 74.2% | **28.3%** |

**결론이 뒤집혔다.** 모든 조건이 1%p 안쪽으로 붙어 있다.

### 3-4. 이 결과의 해석

| 관찰 | 해석 |
|---|---|
| 28건에서는 재현율이 전부 100% | 문제가 너무 쉬웠다. 그 측정은 신뢰할 수 없다 |
| 115건에서 재현율 71~74%로 하락 | 실제 난이도가 드러났다 |
| 조건 간 차이가 1%p 안쪽 | **prefetch 전략은 더 이상 병목이 아니다** |
| 정밀도 17%대에서 정체 | 병목은 점수 함수 자체다 |

**따라서 다음 작업 방향이 데이터로 정해졌다.**
프리페치 전략을 더 튜닝하는 것은 의미가 없고,
점수 함수(키워드 매칭 → 형태소 분석 → BM25 → 임베딩 → 재랭커)를 바꿔야 한다.

> 이것이 "규모를 키우면 결론이 바뀔 수 있다"고 미리 적어둔 이유다.
> 28건 수치를 발표에 썼다면 잘못된 결론을 보고할 뻔했다.

## 4. 점수 함수 상수

`memory_store._score()`의 값들이다. **전부 임의값이고 검증되지 않았다.**

| 상수 | 값 | 등급 | 비고 |
|---|---|---|---|
| 토큰 일치 | `1.0 + log1p(빈도)` | 관례 | TF 가중의 표준 형태 |
| 제목 포함 | **기본 없음** (`add`면 +2.0) | 실측 | 09-15 Allganize dev(LTM 단독)에서 +2.0 / ×1.1 상한 / 없음이 동률이고, 09-16 에이전트 전체에서는 +2.0이 LTM 점수만 부풀려 계층 병합을 무너뜨렸다(07 문서 2-3절) → **기본값을 `none`으로 변경**, `RETRIEVER_TITLE_BONUS=add`로 되돌릴 수 있다 |
| 프로젝트명 포함 | `+1.5` | **임의** | LTM은 문서의 `project` 필드 기준. 필드가 없는 코퍼스에서는 0 |
| 최신성 | `max(0, 4.0 - 경과일 × 0.5)` | **임의** | 8일이 지나면 0이 된다 |

최신성 보정은 질문에 "아까/오늘/최근"이 있을 때만 적용한다.

**계층 보정은 제거했다.** 예전에는 `계층==ltm && 공식어 → +2.0` 같은 보정이
있었는데, 계층 신호가 세 곳(쿼리 주입 / 점수 보정 / prior)에서 중복 적용되고 있었다.
지금은 prior 한 곳에서만 적용한다.

### 아직 없는 요소

일반적인 랭킹 점수는 네 요소로 구성한다.

```
Score = w1·관련성 + w2·최신성 + w3·참조빈도 + w4·피드백
```

현재 앞의 두 개만 있다. 뒤의 두 개는 확보 방법이 있다.

| 요소 | 확보 방법 | 비용 |
|---|---|---|
| 참조 빈도 | `logs/turns/*.json`의 `source_ids` 카운트 | 이미 쌓이는 중 |
| 사용자 피드백 | CLI에 `/good`, `/bad` 추가 | 두 줄 |

## 5. 에이전트 루프

### 5-1. `max_tool_calls = 3`

| 항목 | 내용 |
|---|---|
| 하는 일 | 도구 호출 한도. 루프는 `max_tool_calls + 1`회 돈다 |
| 등급 | **임의** |
| 파생 결과 | **LLM 호출은 턴당 최대 5회** (analyzer 1 + agent 4) |

실측 분포는 대부분 2~3회다. 프리페치가 근거를 미리 넣어주기 때문에
1차 호출에서 답이 나오는 경우가 많다.

**2026-09-28: 이 값이 실제 제한이 아니었다.** 상한에 도달하면 안내 메시지만
덧붙이고 다음 호출에 도구를 계속 넘겼고, 한 응답의 여러 도구 요청을 전부 실행했다.
상한 3회에 8회가 실행되는 것을 재현했다. 지금은 남은 횟수가 0이면 `client.chat`에
`tools`를 넘기지 않고, 한 응답 안에서도 남은 횟수만 실행한다.
값 자체는 그대로 3이다 — 값의 근거가 생긴 것이 아니라 값이 지켜지게 된 것이다.

| 등급 | **임의** |

| 항목 | 내용 |

## 6. 컨텍스트

### 6-1. `CONTEXT_MODE = full`

| 모드 | 1차 컨텍스트 | 크기(실측) |
|---|---|---|
| `full` | 원문 8건 전량 | 5,770자 |
| `hybrid` | 상위 2건 원문 + 나머지 요약 | 4,523자 |
| `summary` | 요약만 | 3,836자 |

| 항목 | 내용 |
|---|---|
| 등급 | **미측정** |
| 현재 기본값 | `full` — 비교 기준선이므로 기본으로 둔다 |
| 결정 방법 | 원문 확장률을 재서 정한다 (아래) |

**어느 모드가 나은지는 아직 모른다.** 확장이 자주 일어나면 LLM 호출이
2회가 되면서 절감이 사라지기 때문이다.

| 확장률 | 채택 |
|---|---|
| 30% 미만 | `summary` |
| 30~70% | `hybrid` |
| 70% 초과 | `full` 유지 + 요약 품질 개선 |

이 판단 기준의 경계값(30%, 70%)도 **임의**다.

### 6-2. `HYBRID_FULL_CARDS = 2`

| 항목 | 내용 |
|---|---|
| 하는 일 | hybrid 모드에서 원문을 넣을 상위 문서 수 |
| 등급 | **임의** |
| 근거 | "실제로 쓰이는 근거는 보통 1~2건"이라는 관찰. 검증 안 됨 |

### 6-3. 근거 전달 예산 — `CONTEXT_MAX_EVIDENCE_CHARS`, `LTM_EXCERPT_CHARS`, `LTM_CHUNKS_PER_DOC`

세 값이 함께 **모델이 실제로 읽는 글자 수**를 정한다. 2026-09-28까지 셋 다
코드에 박혀 있어서 재는 것 자체가 불가능했다. 설정으로 뺐다.

| 파라미터 | 기본값 | 등급 | 하는 일 |
|---|---:|---|---|
| `CONTEXT_MAX_EVIDENCE_CHARS` | 7000 | **임의** | 근거 블록 전체 상한. 넘치면 뒷순위 카드가 빠진다 |
| `LTM_EXCERPT_CHARS` | 600 | **임의** | 카드 한 장의 본문 길이 |
| `LTM_CHUNKS_PER_DOC` | 1 | **임의** | 한 문서에서 보여 줄 대목 수 |
| `max_recent_turns` | 4 | **임의** | 세션 캐시 8턴 중 4개만 넣는다 |
| `summary` / `quote` | 220자 | **임의** | 카드 머리말 |

**왜 이 값들이 문제였나.** 셋이 겹쳐서 문서를 세 번 자른다.

1. 문서 하나에서 **대표 청크 1개**만 카드가 된다. Allganize 문서는 청크가
   16~68개다 — 문서의 2~6%만 보여 주고 답하라는 뜻이다.
2. 그 청크를 **600자**로 자른다. Allganize 청크 2,960개 중 1,079개(36.5%)가
   600자를 넘고, 잘려나가는 글자가 합계 294,714자다.
   — **다만 2026-10-06 분해에서 이 손잡이는 전달에 기여하지 않았다.** 아래 참조.
3. 카드 여러 장이 **7,000자**를 넘으면 뒷순위가 빠진다. 20문항 중 15건에서
   후보 8건 중 6~7건만 들어갔다.

**전달 단계만 따로 측정했다** (`evidence_delivery_check.py`, LLM 없음, 20문항).
질의 분석은 규칙 기반으로 고정해 실행 간 차이를 없앴다.

| chunks / excerpt / max | 주입/후보 | 근거글자 | 문서 전달 | 정답 페이지 본문 전달 |
|---|---|---:|---|---|
| 1 / 600 / 7000 (기존) | 5.5 / 6.2 | 5,319 | 19/20 | **17/20** |
| 1 / 1200 / 12000 | 6.2 / 6.2 | 6,847 | 19/20 | 17/20 |
| 2 / 600 / 12000 | 5.7 / 6.2 | 8,922 | 19/20 | 17/20 |
| 3 / 600 / 20000 | 6.2 / 6.2 | 13,258 | 19/20 | 18/20 |
| **4 / 600 / 24000** | **6.2 / 6.2** | **16,733** | 19/20 | **19/20** |
| 8 / 600 / 45000 | 6.2 / 6.2 | 30,358 | 19/20 | 19/20 |

읽을 것이 세 가지다.

- **깊이가 넓이보다 효과가 크다.** 발췌를 길게 늘리는 것(1/1200)은 전달을 전혀
  올리지 못했고, 같은 문서의 다른 대목을 넣는 것(3~4개)이 올렸다. 정답이 대표 청크
  **밖**에 있는 것이 문제였고, 대표 청크가 짧아서 잘린 것이 아니었다.
- **4개에서 포화한다.** 남은 1건(q_4)은 문서 자체가 검색되지 않은 경우다.
  전달 단계에서 더 얻을 것이 없다 — 그 1건은 검색 문제다.
- **깊이와 넓이는 상한을 두고 경쟁한다.** 상한을 고정하고 대목을 늘리면 주입 카드
  수가 줄어든다(1/600/7000에서 5.5 → 4/600/16000에서 4.6). 그래서 상한도 같이 올려야
  한다.

**기본값은 아직 바꾸지 않았다.** 근거글자가 3.1배가 되므로 답변 품질이 그만큼
좋아지는지 확인해야 한다. 20문항 실측 결과는
`llm_study/260919-0930/04-근거-전달-경로-수정.md`에 있다.

### 6-3-0. 셋 중 무엇이 일했나 (2026-10-06, 60문항 · LLM 없음)

세 손잡이를 **한 번에 하나씩** 열어 9개 조건을 돌렸다. 표기는
`대목 수 / 청크 발췌 / 전체 상한`이고, **본문 전달**은 정답 페이지 글이 전달된 문항 수다.

| 조건 | 본문 전달 | 주입 평균 | 탈락 | 근거 글자 |
|---|---:|---:|---:|---:|
| `1 / 600 / 7,000` 기준선 | 46 | 5.1 | 34 | 4,897 |
| `1 / 600 / 24,000` 상한만 | **46** | 5.7 | 0 | 5,449 |
| `1 / 무제한 / 7,000` 발췌만 | **46** | 4.5 | 68 | 4,898 |
| `2 / 600 / 7,000` | 49 | 3.5 | 134 | 5,295 |
| `4 / 600 / 7,000` 대목만 | **55** | 1.9 | 224 | 5,102 |
| `4 / 600 / 12,000` | **56** | 3.5 | 132 | **9,156** |
| `4 / 600 / 24,000` 현재 | 56 | 5.7 | 0 | 15,093 |
| `4 / 무제한 / 24,000` | 56 | 5.1 | 34 | 16,367 |

**결론 셋.**

1. **`LTM_CHUNKS_PER_DOC`만 전달을 올린다.** 1 → 2 → 4가 46 → 49 → 55/56으로 단조 증가.
   정답이 대표 청크 밖에 있었다는 진단이 그대로 확인된다
2. **`CONTEXT_MAX_EVIDENCE_CHARS`는 혼자서는 0건이다.** 역할이 다르다 — 대목을 늘리면
   카드가 커져 뒷순위가 탈락하는데(상한 7,000에서 탈락 224, 주입 1.9장),
   상한을 올리면 그 탈락이 0이 된다. **깊이는 대목 수가, 폭은 상한이 정한다**
3. **`LTM_EXCERPT_CHARS`는 기여가 없다.** 무제한으로 열어도 전달이 같고 글자만 늘어난다.
   외부 리뷰의 첫 지적이었고 "600자 초과 청크 36.5%"는 사실이었지만,
   **정답 페이지의 글은 600자 안쪽에 있었다**

유형별로는 이미지형이 5/11 → **9/11**로 대목 수만으로 올랐다. 표형은 9/10에서
전 조건 고정이고, 남은 1건은 표 자체가 이미지인 경우다.

그리고 **상한 24,000은 과하다.** `4 / 600 / 12,000`이 같은 56건에 근거 글자가
39% 적다. 다만 주입이 5.7 → 3.5장으로 줄어 "여러 근거를 모아야 하는 질문"에서
손해일 수 있고, 그 손실은 이 지표에 잡히지 않는다. 답변 품질로만 가를 수 있다.

### 6-3-0-1. `SEED_EXCERPT_CHARS = 0` (2026-10-07)

| 항목 | 내용 |
|---|---|
| 하는 일 | 시드 문서(`memory_root/{stm,mtm,ltm}/`) 카드의 본문 길이 |
| 기본값 | **0 — `LTM_EXCERPT_CHARS`를 따른다**(이전과 같은 동작) |
| 등급 | **측정** |
| 근거 | 20문항에서 답 전달 17/20 → **20/20** (600 → 6,000자) |

**왜 나눴나.** 청크 코퍼스와 시드 문서는 모양이 다르다. 청크는 `LTM_CHUNKS_PER_DOC`으로
대목을 늘릴 수 있지만, **시드 문서는 파일 하나가 카드 하나**라 그 손잡이가 걸리지 않는다.
발췌 길이가 유일한 손잡이인데 한 값을 Allganize와 공유하고 있어서, 시드를 손보려고
올리면 공개 평가셋 측정까지 같이 움직였다.

진행 과제 시드의 LTM 문서는 평균 **21,582자**다. 발췌 600자면 문서의 **2.8%**다.

| 시드 발췌 / 전체 상한 | 답 있는 문서 후보 | **전달된 글자에 답** |
|---|---:|---:|
| 600 / 7,000 | 20/20 | 17/20 |
| 2,000 / 12,000 | 20/20 | 19/20 |
| **6,000 / 24,000** | 20/20 | **20/20** |

6,000자에서 전달이 검색을 그대로 따라간다. 다만 그것은 **지금 문서 길이에서** 그렇다는
뜻이다 — 6,000자는 평균 문서의 28%이고, 답이 뒤쪽에 있는 문서가 들어오면 다시 깨진다.
그때는 계층별 청크 코퍼스를 붙이는 쪽을 검토한다.

### 6-3-1. 도구 결과 예산 — `TOOL_RESULT_EXCERPT_CHARS`, `TOOL_RESULT_CHUNKS_PER_DOC`

| 파라미터 | 기본값 | 등급 | 하는 일 |
|---|---:|---|---|
| `TOOL_RESULT_EXCERPT_CHARS` | 600 | **측정** | `retrieve_memory` 결과 카드의 본문 길이 |
| `TOOL_RESULT_CHUNKS_PER_DOC` | 1 | **측정** | 그 카드가 실을 대목 수 |

위 6-3의 세 값은 **1차 컨텍스트**를 정한다. `retrieve_memory` 결과는 같은 검색 경로를 타므로
같은 예산이 걸려 있었는데, **그게 비용의 절반을 먹었다.**

2026-09-29 실측(20문항). 1차 컨텍스트를 3배로 키웠을 때 함께 일어난 일이다.

| | 기본 | 전달(1차만 키움) | 배수 |
|---|---:|---:|---:|
| 1차 컨텍스트 | 6,992자 | 20,932자 | 3.0배 |
| `retrieve_memory` 결과 | 8,005자 | 18,858자 | **2.4배** |
| 입력 토큰 평균 | 61,827 | 132,836 | 2.15배 |
| 출력 토큰 평균 | 4,054 | 4,216 | 1.04배 |

두 곳의 비용 성격이 전혀 다르다.

- 1차 컨텍스트는 카드 **8장**이고 턴에 **한 번** 만들어진다.
- 도구 결과는 카드 **10~20장**이고, 재검색이 있으면 누적 메시지로 **호출마다 다시 실린다.**

그래서 같은 깊이를 주면 도구 결과가 훨씬 비싸다. 정답에 기여한 근거는 1차 컨텍스트 쪽이었다
(이미지 유형 2건이 정답이 된 것은 대표 청크 밖의 대목이 1차 컨텍스트에 실렸기 때문이다).

**자르는 위치를 옮겼다.** 카드를 만드는 지점(`LtmCorpus._card`)이 아니라 **쓰이는 지점**
(`AgentRuntime._trim_tool_result`)에서 자른다. 검색 결과 자체는 그대로 두고 모델에게 보낼 때만
줄인다. 잘린 쪽이 로그에도 남는다 — 09-28에 정한 "기록은 실제로 전달한 것"과 같은 규칙이다.

한국어 글자를 토큰으로 환산하는 비율도 같이 재 뒀다. **글자 1자 ≈ 입력 토큰 2.0개**
(호출 수가 같은 17문항, 중앙값 1.98, 범위 0.90~2.34). 예산을 글자로 세면 비용이 작아 보인다 —
`CONTEXT_MAX_EVIDENCE_CHARS=24000`은 실제로 **호출당 약 47,400 입력 토큰**이다.

### 6-3-2. 도구 결과 중복 제거 — `TOOL_RESULT_DEDUPE`, `TOOL_RESULT_TOP_K_CAP`

| 파라미터 | 기본값 | 등급 | 하는 일 |
|---|---:|---|---|
| `TOOL_RESULT_DEDUPE` | 0 (꺼짐) | **측정** | 이미 전달한 문서를 도구 결과에서 빼고 뒤 순위로 채운다 |
| `TOOL_RESULT_TOP_K_CAP` | 0 (제한 없음) | **측정** | 모델이 요청할 수 있는 `top_k` 상한 |

도구 결과를 얕게 만든 뒤에도(6-3-1) 남은 글자의 **69%가 중복**이었다.

| qid | 도구 카드 | 그중 이미 전달한 문서 |
|---|---:|---:|
| q_180 | 5장 | **5장 (100%)** |
| q_75 | 11장 | 9장 (82%) |
| q_126 | 20장 | 13장 (65%) |
| q_106 | 20장 | 12장 (60%) |
| **합계 (9문항)** | **96장** | **66장 (69%)** |

그리고 재검색한 9문항 중 **8문항은 이미 prefetch에 정답 문서가 들어와 있었다.**
모델은 근거가 부족하다고 판단해 다시 찾는데, 검색기가 **같은 문서를 또 돌려준다.**

**이미 프롬프트에 있는 내용이므로 빼도 모델이 잃는 정보가 없다.** 다만 두 가지를 같이 처리해야 한다.

1. 중복만 지우면 결과가 **빈 목록**이 되는 경우가 생긴다(q_180). 모델은 "찾아도 아무것도
   없다"로 읽어 한 번 더 검색하고, 재검색은 컨텍스트 전체를 재전송하므로 아낀 것보다 더 쓸 수 있다.
   그래서 **넉넉히 받아 온 뒤 잘라** 요청한 장수를 유지한다(`fetch_k = max(top_k*3, top_k+5)`).
2. `top_k` 상한. 모델은 20까지 요청한다(58회 중 3회). 1차 컨텍스트가 8장인데 도구 결과가
   20장이면 그쪽이 더 무겁고, 그 2문항이 가장 비싼 문항이었다.

측정 결과는 `llm_study/260919-0930/08-도구-결과-중복-제거.md`에 있다.

### 6-3-2-1. 세션 전달 원장 — `SESSION_EVIDENCE_LEDGER` 외 2개 (2026-10-06)

| 파라미터 | 기본값 | 하는 일 |
|---|---:|---|
| `SESSION_EVIDENCE_LEDGER` | **0** | 앞선 턴에 본문을 준 문서를 참조 카드로만 넣는다 |
| `SESSION_LEDGER_MAX_DOCS` | 200 | 원장에 남길 문서 수. 넘치면 오래된 턴부터 버린다 |
| `SESSION_LEDGER_MIN_BODIES` | 2 | 원장을 켜도 한 턴에 보낼 최소 본문 장수 |

**왜 필요한가.** 지금까지의 중복 제거(`TOOL_RESULT_DEDUPE`)는 **한 턴 안에서만** 돌았다.
`seen_tier_queries`와 `AgentTrace`가 턴마다 새로 만들어지기 때문이다. 턴이 넘어가면
prefetch가 백지에서 같은 문서를 다시 가져와 본문을 또 싣는다.

**설계에서 조심한 세 가지.**

1. **숨기지 않고 줄인다.** 이미 준 문서는 제목·출처·`delivered_in_turn`만 남긴 참조
   카드로 들어가고, 모델이 필요하면 `expand_evidence`로 되불러온다. 목록에서 아예
   빼면 모델이 "그 문서는 없다"로 읽고 같은 검색을 다시 한다(2026-09-29 q_180)
2. **참조로 빈 자리를 새 문서가 채운다.** `MemoryPrefetcher._cap()`이 상한을
   **새 문서 기준**으로 센다. 안 그러면 턴이 쌓일수록 새 근거가 0장이 되고
   2턴째가 1턴째보다 정보가 적어진다
3. **본문 0장을 만들지 않는다.** 새로 볼 문서가 없으면 상위 참조를 본문으로 되돌린다.
   이전 턴의 본문은 메시지에 남지 않기 때문이다(턴마다 messages를 새로 만든다)

원장을 켜면 `full` 모드에서도 `expand_evidence`를 등록한다. 참조만 보여 주고
본문 경로를 막으면 "근거 없음"으로 답하게 된다.

**측정(목 LLM, 3턴).** 턴 간 재전송은 0이 되지만 절감은 작다 — 중복은 질문이 밀착할
때만 생기고, 빈 자리를 새 문서가 채우므로 줄어든 글자의 일부가 되돌아온다.

| 시나리오 | 턴 간 재전송 | 본문 글자 |
|---|---|---|
| 서로 다른 주제 | 0 → 0 | ±0% |
| 같은 대상을 파고드는 후속 | 2 → **0** | −3.0% |
| 거의 같은 질문 반복 | 5 → **0** | **−12.3%** |

진짜 이득은 토큰이 아니라 **같은 예산에 새 문서를 더 본다**는 쪽이다. 기본값이 꺼짐인
이유는 실제 호출 세션 로그 201개가 **전부 1턴**이어서, 멀티턴 효과를 아직 못 쟀기 때문이다.

### 6-3-3. `PREFETCH_TOP_K = 8`은 재검토 대상이다

2026-09-29에 **주입한 근거와 답변이 인용한 근거를 분리해 기록**하게 만든 뒤 처음 잰 값이다.

| | |
|---|---:|
| 주입 평균 | 7.0장 |
| **답변이 인용한 평균** | **1.1장 (15%)** |
| 인용된 카드 순위 | 1위 17회 · 2위 4회 · 3위 1회 · **4위 이하 0회** |
| 정답 문서 순위 | 1위 17건 · 2위 2건 · **3위 이하 0건** |

**4위 이하 카드는 20문항에서 한 번도 인용되지 않았고 정답 문서도 없었다.** 그런데 자리 5개를
차지하고 토큰을 먹는다.

다만 **"인용되지 않았다"와 "없어도 같은 답이 나온다"는 다르다.** 모델이 8장을 비교해 1위를
고른 것일 수 있다. 4장만 주면 다른 선택을 할 수도 있다. 01 문서에서 이 값 축소를 "하지 않기로"
결정했던 이유가 "정답 포함률에 안 잡히는 품질 손실"이었고, 그때는 그것을 잴 수단이 없었다.
지금은 있으므로 **재고 결정한다.** 아직 바꾸지 않았다.

|---|---|---|---|
| `SESSION_CACHE_TURNS` | 8 | 임의 | 세션 파일에 보관할 턴 수 |
| `QUERY_ANALYZER_MAX_TOKENS` | 4096 | **측정** | 2048에서는 JSON이 잘려 파싱 실패가 났다 |

`QUERY_ANALYZER_MAX_TOKENS`는 실패를 통해 정해진 값이다.
처음 2048로 두었더니 모델이 상한까지 출력하고도 JSON을 끝내지 못해
`Expecting value: line 1 column 1` 오류로 fallback했다.

상한 자체가 필요한 이유는 상한이 없을 때 completion이 8,192 토큰까지
치솟는 경우를 관찰했기 때문이다.

## 8. mock 토큰 추정

| 항목 | 값 | 등급 |
|---|---|---|
| `CHARS_PER_TOKEN` | 2 | **임의** |

한국어는 토크나이저에 따라 1자당 0.7~1.5 토큰이라 이 값은 상당한
과소추정일 수 있다. 그래서 mock이 만든 토큰에는 `estimated: true`가 붙고,
평가 스크립트가 이를 경고로 출력한다.

**mock 토큰으로 절감률을 계산해서는 안 된다.**

## 9. 계층 가중치 (규칙 기반 analyzer)

질문 유형별로 계층 비중을 정한다. **전부 임의값이다.**

| 의도 | STM | MTM | LTM | 판정 조건 |
|---|---|---|---|---|
| `session_context_answer` | 0 | 0 | 0 | 세션 참조 + 요약 요청 |
| `memory_comparison` | 0.35 | 0.25 | 0.40 | 충돌/비교/차이 |
| `recent_context_lookup` | 0.65 | 0.25 | 0.10 | 아까/오늘/최근 |
| `official_knowledge_lookup` | 0.10 | 0.20 | 0.70 | 공식/최종/기준/지침 |
| `working_document_lookup` | 0.20 | 0.65 | 0.15 | 회의록/초안/보고서 |
| `organization_memory_lookup` | 0.34 | 0.43 | 0.23 | 그 외 검색 필요 |
| `direct_answer` | 0 | 0 | 0 | 개념/뜻/일반적으로 |

측정 결과 α=0(계층 무시)과의 F1 차이가 0.3%p에 불과하므로,
**이 표를 정교하게 다듬는 것보다 검색기를 바꾸는 것이 우선이다.**

## 10. 안전 설계의 근거

수치는 아니지만 판단 기준이므로 함께 남긴다.

### 10-1. 실패 방향의 비대칭

> 불필요한 검색은 토큰을 더 쓸 뿐이지만,
> 필요한 검색을 건너뛰면 근거 없이 답하게 된다.

이 원칙 때문에 다음이 모두 "검색하는 쪽"으로 기울어져 있다.

- 규칙 analyzer: 신호가 없으면 `memory_needed = True`
- LLM 방어: 규칙이 검색 필요라고 보면 LLM이 아니라고 해도 검색 유지

**대가**: "일반적으로 프로젝트 관리 개념이 뭐야?" 같은 질문에서
`MEMORY_MARKERS`에 "프로젝트"가 있어 불필요하게 검색한다.
평가에서 이 실패를 확인했지만 고치지 않았다. 반대 방향 실패가 더 나쁘기 때문이다.

### 10-2. LLM 출력 방어 5종

실제 관찰된 오작동에 대응해 넣었다.

| 관찰된 오작동 | 방어 |
|---|---|
| `project: "assignment_a"` (과제명 영어 번역) | 어휘 목록에 없으면 규칙 추출값으로 |
| 검색 필요한 질문을 `session_only`로 분류 | 검색 유지로 복원 |
| 스키마 밖 `{"type": "deadline"}` 생성 | 허용 키 4개만 통과 |
| completion 8,192 토큰 폭주 | `max_tokens` 상한 |
| HTTP 429 | 규칙 기반 대체 + `fallback_used` 기록 |

**2026-09-28: 이 방어가 실제 경로에서 반쯤 빠져 있었다.**

`RuleBasedQueryAnalyzer`에는 코퍼스 과제명 목록으로 오탐을 막는 장치가 있다.
`PROJECT_RE`가 "한 단어 + 과제/사업"을 잡는데 일반 명사도 걸리기 때문이다
("이 과제", "총 사업", "연구개발 과제", "산업기술혁신 사업").

그런데 `LLMQueryAnalyzer`가 내부 fallback을 만들 때 그 목록을 넘기지 않았다.
게다가 `_safe_filters`가 fallback의 project로 LLM 결과를 **무조건 덮어썼다.**
결과: 실제 실행에서 `project="이 과제"`가 필터로 들어가 모든 문서가 0.3배로 감점됐다.

지금은 fallback에도 같은 목록을 넘기고, 목록이 있으면 LLM 값이 그 안에 있는지
확인해 먼저 쓴다. 목록이 없을 때는 예전처럼 fallback을 쓴다 — 확인할 수 없는 값을
통과시키면 번역된 과제명이 다시 들어온다.

`date_range`는 허용 키에서 뺐다(4개). 스키마에는 있었지만 `MemoryStore`도
`LtmCorpus`도 해석하지 않아서, 로그에는 날짜 조건이 걸린 것처럼 남고 검색은 무시했다.

`공통` 문서 필터도 같은 성격의 결함이었다. `LtmCorpus._filter_weight`가 비교 방향을
뒤집어 써서(`필터값`이 공통인지를 봄) A 과제 질문에서 **조직 공통 문서가 감점됐다.**
규정·양식·지침이 바로 그 공통 문서다. `MemoryStore`는 처음부터 문서 쪽을 보고 있었다.

### 10-3. analyzer 프롬프트에서 규칙 결과를 뺀 이유

처음에는 프롬프트에 `fallback_reference`로 규칙 기반 결과를 통째로 넣었다.
그 결과 **4개 질문 전부 규칙과 완전히 동일한 답**이 나왔고 4,272 토큰을 썼다.
작은 모델은 완성된 답이 주어지면 그대로 복사한다.

제거하자 3/4에서 다르게 판단했고, 그 차이가 위 10-2의 오작동들이었다.
**LLM analyzer가 규칙 기반보다 낫다는 근거는 아직 없다.**

## 12. 값을 바꿀 때의 절차

1. 이 문서에서 해당 값의 등급과 근거를 확인한다
2. `python eval/run_eval.py`로 변경 전 값을 기록한다
3. 값을 바꾸고 다시 측정한다
4. **문서 수와 케이스 수를 함께 기록한다.** 규모가 다르면 비교할 수 없다
5. 이 문서를 갱신한다

```bash
# 현재 기준선
python eval/run_eval.py --json runs/baseline-prior.json

# 파라미터 비교 예시
python eval/run_eval.py --alpha 0
python eval/run_eval.py --tier-floor 2
python eval/run_eval.py --mode quota
```
